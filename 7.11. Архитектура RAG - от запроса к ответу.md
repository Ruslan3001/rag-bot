В основе RAG лежит простая и в то же время амбициозная идея — совместить **поиск по векторному индексу с генеративной моделью**. Чтобы не заставлять LLM «помнить» абсолютно всё на свете, для неё создаётся внешний источник «знания» — векторная база, где каждый документ хранится как эмбеддинг. Когда от пользователя приходит запрос, сначала находятся наиболее релевантные векторы (retrieval). И только после этого они передаются в контекст генератора (augmented generation). Здесь вступают в игру специализированные хранилища:

- **FAISS** — минималистичный и очень быстрый движок для C++ или Python.
- **Pinecone** — полностью управляемый облачный сервис‑хранилище векторных данных (SaaS).
- **Qdrant** — полнофункциональный векторный сервер со скалируемыми REST-и gRPC-API.
- **ChromaDB** — легко встраиваемое решение с богатой экосистемой в Python.
    

В этом уроке мы вместе построим полный RAG-pipeline: подготовим и загрузим данные, сделаем однопроходную (single-pass) индексацию, ранжируем кандидатов, проведём постфильтрацию и, наконец, интегрируем всё с генеративной моделью.

## **Самый простой вариант**

Если перед вами стоит задача построить полный RAG-pipeline, то первое, о чём вы должны подумать, — это FAISS.

**FAISS** — это своеобразный локальный карманный «поисковик по смыслам»: скачиваете, подключаете и сразу можно запускать поиск по эмбеддингам без сервера и регистрации. Библиотека появилась в Facebook AI и с тех пор стала стандартом-де-факто для первых экспериментов с векторным поиском.

Главное понятие в FAISS — индекс. Это специальная структура данных, которая компактно упаковывает векторные представления и хранит вспомогательную информацию (кластеры, графы, кодбуки и т. д.), чтобы найти ближайшие векторы, не перебирая каждый раз весь массив.

То есть индекс в FAISS — это не просто «список эмбеддингов», а инженерный приём, который заранее организует пространство. Благодаря этому поиск превращается из O(N)O(N)O(N) в «пару десятков операций» даже на миллионах точек.

Образно говоря, вы строите индекс, кладёте в него вектор и как бы спрашиваете: «Кто к этому новому вектору ближе всех?» При этом базовый сценарий помещается буквально в пять строк кода:

```
import faiss
import numpy as np

# наши «документы» — 5-мерные эмбеддинги
embeddings = np.random.randn(10, 5).astype('float32')

# создаём индекс «cosine = L2 после нормализации»
faiss.normalize_L2(embeddings)
index = faiss.IndexFlatIP(5)          # IP = inner product ≈ cosine
index.add(embeddings)                # кладём 10 векторов в индекс

# ищем 3 ближайших к новому запросу
query = np.random.randn(1, 5).astype('float32')
faiss.normalize_L2(query)
distances, ids = index.search(query, k=3)

print(ids)          # индексы соседей
print(distances)    # косинусные близости 
```

Этот пример генерирует рандомные слова и ищет среди них то, что похоже на другое рандомное слово, которое пришло на вход. Это показывает простоту и краткость работы с FAISS. А дальше вы уже можете поиграться с гипотезами: что будет, если увеличить размерность, сменить метрику или попробовать другой тип индекса (HNSW, IVF, PQ)?

### FAISS стоит применять

- **Нужны скорость и автономность.** Всё происходит локально: нет сетевых задержек и данные никуда не уходят.
- **Требуется полный контроль.** Выбираете алгоритм, тюнингуете параметры и собираете статистику, поэтому FAISS отлично подходит, чтобы глубоко понять, как работает ANN (Approximate Nearest Neighbor).
- **Вы хотите лёгкого входа.** pip install, пять строк кода и уже можно искать по смыслам.
    

### Когда всплывают ограничения

- **Масштаб и память.** Миллионы векторов всё ещё держатся в памяти, но десятки — сотни миллионов требуют серьёзных ухищрений (шардирование, дисковый индекс, квантование).
- **Фильтрация и метаданные.** У FAISS нет встроенного механизма «найди все векторы автора = Alice и тега = python». Фильтрацию нужно будет проводить самостоятельно (маски, отдельные списки id, кастомная логика).
- **Обновление индекса.** Локально живущие файлы придётся синхронизировать и бэкапить вручную, если команда работает распределённо.

## Векторные системы управления базами данных

Когда прототипы на FAISS становятся слишком тяжёлыми, в игру вступают настоящие «векторные системы управления базами данных». Самые популярные — Pinecone, Qdrant и Chroma. Сравним все три с FAISS:

|База|Языки API|Фильтрация|Метаданные|Скорость|Развёртывание|
|---|---|---|---|---|---|
|**FAISS**|C++, Python (обёртки для Java/JS от сообщества)|Нет встроенной; возможна битсет-маска/постфильтрации|Не хранит, требуется внешнее хранилище|Сверхбыстрая in-process (C++)|pip install faiss или conda, локально/on-prem|
|**Pinecone**|Python, Node, Go, Java|JSON-фильтры (=, range, list)|До 4 KB JSON на вектор|Высокая, но зависит от сети (SaaS)|Требуется буквально только завести аккаунт и доступ к облаку|
|**Qdrant**|REST, gRPC, Python, JS|Сложные условия, числовые диапазоны, geo|Типизированный payload, любой размер|Один из лидеров бенчмарков (Rust)|
|**Chroma**|Python, JS|and/orand/or фильтры, простые условия|Произвольный JSON|Очень быстрая in-process, скейл ограничен RAM|

### Какой метод выбрать

Если нужно быстро прототипировать и понять матчасть, но при этом вы не хотите иметь дело с облаками, то рекомендуем начинать с **FAISS**.

**Pinecone** подойдёт, когда нужна «база как сервис»: масштаб, резервирование и SLA на отдачу. Вы платите за хостинг и не думаете про железо. Однако есть и свои минусы: интернет-латентность и отсутствие on-prem.

**Qdrant** — открытый исходник на Rust, одна команда Docker-run для старта, богатая фильтрация (в том числе geo) и ведущие показатели скорости. Подходит как для локальной разработки, так и для продакшена — просто переключаетесь на managed-кластер, когда требуется.

**Chroma** — «Pythonic» вариант: всё живёт в процессе, идеально интегрируется с LangChain, прозрачен для быстрых PoC. Однако в тот момент, когда коллекция состоит уже из десятков миллионов векторов, придётся мигрировать куда-то ещё.

Теперь, когда вы познакомились с каждым инструментом, давайте рассмотрим конкретные кейсы для каждого.

### **FAISS — быстрый научный PoC**

Небольшая команда R&D анализирует 1,5 миллиона научных статей, чтобы строить «semantic citation graph».

**Особенности задачи:**

- Данные локальны (GPU-сервер уже стоит в лаборатории).
- Нужно быстро перебирать разные размеры эмбеддингов и индексов (IVF, HNSW, PQ).
- Всё крутится в Jupyter, результаты сразу в ноутбук.

**Почему FAISS?**

- Один pip install faiss-gpu, дальше Python-обёртка и прямой доступ к C++-ядру.
- На том же сервере можно хранить 200 млн векторов без сети/облака.
- Легко «выкинуть» эксперимент и собрать новый, не боясь счётчика $.

**Итог**

- Прототип за неделю → статья + пост в блоге.
- Когда появился production-интерес, мигрировали в Qdrant, оставив FAISS только для офлайн-research.
    

### **Pinecone — SaaS-продукт с SLA**

Стартап делает B2B-чат-боты «под ключ» для банков и e-commerce

**Особенности задачи:**

- Порядка 50 отдельных индексов (по клиентам), общий объём — примерно три миллиарда векторов.
- Спрос скачет: ночью мало запросов, на чёрную пятницу — пиковые.
- Контракты требуют ≥99.9% аптайма и «золотой» бэкап.

**Почему Pinecone?**

- «Выкинуть» кластер в US-East и EU-West одним API-звонком.
- Автоматическое реплицирование, бэкапы и метрики из коробки.
- Pay-as-you-go: оплачивают лишь активные поды, не держат «холостой» железо.

**Итог**

- Свою DevOps-команду не расширяли — следят за latency только через dashboards Pinecone.
- Ценник выше self-host, но покрывается маржой за SLA.
    

### **Qdrant — geo-фильтрация и on-prem → cloud**

Логистическая платформа ищет ближайший склад, если клиент спрашивает «доставка сегодня».

**Особенности задачи:**

- Каждый вектор содержит (lat, lon) + товарные признаки.
- PoC разворачивали в локальном офисе (доступ в интернет ограничен политикой).
- Через полгода стартовал международный филиал → нужна облачная копия.

**Почему Qdrant?**

- Один docker run qdrant/qdrant, и локальный сервис готов.
- Native geo-filter (within_radius, geo_bounding_box) без внешней БД.
- Когда появились филиалы, переключились на Qdrant Cloud и оставили тот же API.

**Итог**

- Запрос «все склады с товарами A или B в радиусе 40 км» < 30 мс на 100 млн точек.
- Единый код-базис для on-prem и managed-кластера, почти ноль миграционных багов.
    

### **Chroma — локальная RAG-надстройка**

Data-инженер собирает личного ассистента для чтения внутренней вики (≈ 70 тыс. страниц).

**Особенности задачи:**

- Работает на MacBook, без внешнего сервера.
- Хотелось мгновенно пересоздавать коллекции при смене модели эмбеддинга.
- Используется LangChain, всё в одном Python-процессе.

**Почему Chroma?**

- «Pythonic» API — вставил в LangChain несколько строк, и индексация пошла.
- Данные хранятся рядом с кодом; переносить базу не нужно.
- Пока < 10 млн векторов — всё помещается в RAM/SSD, latency до 10 мс.

**Итог**

- MVP был собран за вечер, после чего последовали несколько месяцев личного использования.
- Когда захотелось делиться ассистентом с командой, инженер перешёл на Qdrant Cloud без переписывания логики запросов.

## Разворачиваем Qdrant за минуту

```
# 1. Поднимаем сервер
docker run -d --name qdrant -p 6333:6333 qdrant/qdrant

# 2. Подключаемся клиентом
pip install qdrant-client

python - <<'PY'
from qdrant_client import QdrantClient
import numpy as np, uuid

client = QdrantClient(url="http://localhost:6333")

# 3. Создаём коллекцию на 384-мерных векторах
client.recreate_collection(
    collection_name="docs",
    vectors_config={"size": 384, "distance": "Cosine"}
)

# 4. Загружаем данные с метаданными
points = [
    {
        "id": str(uuid.uuid4()),
        "vector": np.random.rand(384).tolist(),
        "payload": {"author": "Alice", "topic": "RAG"}
    }
    for _ in range(10)
]
client.upsert(collection_name="docs", points=points)

# 5. Ищем ближайшие, фильтруя по автору
hits = client.search(
    collection_name="docs",
    query_vector=np.random.rand(384).tolist(),
    limit=3,
    query_filter={"must": [{"key": "author", "match": {"value": "Alice"}}]}
)
print([h.id for h in hits]) 
```

Этого достаточно, чтобы локально хранить сотни миллионов векторов (дисковый HNSW или ScaNN-индекс) и применять сложные фильтры без дополнительных сервисов.

### **Почему всё это важно для RAG**?

RAG-цепочка живёт на качественном поиске: быстрый nearest neighbor и фильтры по свежести, пользователю и теме. Если векторная БД не умеет выдержать нагрузку или не поддерживает нужные фильтры, то модель начнёт галлюцинировать и предлагать неактуальные куски.

Понимание сильных и слабых сторон каждой системы помогает не только выбрать правильный движок, но и спланировать миграцию, когда стартап вырастет из ноутбука в продакшн-кластер.

## Фильтрация и поиск с учётом метаданных

Когда в векторный поиск добавляют фильтры, он начинает работать куда точнее. Мы всё так же смотрим на смысл близости, но сразу отсекаем лишнее по языку, дате публикации, типу документа, автору и любым другим признакам, которые заранее заложили в метаданные. Это особенно полезно в смешанных коллекциях. Представьте корпоративное хранилище, где русскоязычные FAQ находится вперемешку с англоязычными отчётами и новостями. В таком случае простой векторный поиск вернёт всё подряд, а фильтр оставит только нужный пласт.

Самый частый сценарий — это многоязычный корпус. Если отметить каждый документ коротким ISO-кодом языка (ru, en, de…) и во время запроса добавить условие lang="ru", то на больших коллекциях это даст как минимум двукратный, а то и больший выигрыш по скорости, потому что движок сразу сузит область поиска.

Даты тоже важны, поэтому их следует хранить в одной форме — ISO 8601 (2025-06-01). Тогда вы легко сможете указывать диапазон поиска. Например: «Покажи все статьи за последний квартал». Категорию, тип или статус документа лучше хранить строкой из фиксированного списка (faq, policy, blog). Так будет меньше опечаток и проще настраивать фильтр.

А теперь посмотрим на короткий пример на Qdrant. Задача — найти топ-5 русскоязычных FAQ-ответов за 2024 год:

```
from datetime import date
from qdrant_client import QdrantClient, models

client = QdrantClient(url="http://localhost:6333")

search_result = client.search(
    collection_name="docs",
    query_vector=embedding,          # ваш эмбеддинг запроса
    query_filter=models.Filter(
        must=[
            models.FieldCondition(
                key="lang",
                match=models.MatchValue(value="ru")
            ),
            models.FieldCondition(
                key="type",
                match=models.MatchValue(value="faq")
            ),
            models.RangeCondition(
                key="date",
                gte=date(2024, 1, 1),
                lte=date(2024, 12, 31)
            )
        ]
    ),
    top=5
) 
```

Qdrant применяет фильтр до поиска ближайших соседей, поэтому лишние сегменты базы даже не рассматриваются.

Тот же запрос в Weaviate выглядит так (GraphQL-API плюс параметр nearVector):

```
import weaviate

client = weaviate.Client("http://localhost:8080")

response = (
    client.query
        .get("Document", ["title", "url"])
        .with_near_vector({"vector": embedding, "certainty": 0.7})
        .with_where({
            "operator": "And",
            "operands": [
                {"path": ["lang"], "operator": "Equal", "valueString": "ru"},
                {"path": ["type"], "operator": "Equal", "valueString": "faq"},
                {"path": ["date"], "operator": "GreaterThanEqual", "valueDate": "2024-01-01"},
                {"path": ["date"], "operator": "LessThanEqual", "valueDate": "2024-12-31"}
            ]
        })
        .with_limit(5)
        .do()
) 
```

Weaviate тоже фильтрует до векторного ранжирования, а заодно показывает гибкость GraphQL-синтаксиса. Отсюда возможность комбинировать nearVector, nearText, геофильтры и любые другие условия.

Все эти приёмы работают ровно настолько хорошо, насколько аккуратно описана схема метаданных. Поэтому обратите внимание, что поле «lang» должно быть заполнено всегда, иначе часть документов выпадет из результатов.

При этом данные следует сохранять в одном формате, а категории брать из закрытого набора значений. Если метаданные хаотичны, то пользователей будут ждать пропажи релевантных ответов, которые на самом деле просто оказались без тега. Поэтому при проектировании хранилища нужно изначально решить три вещи: какой набор полей будет у каждого объекта, какие типы у этих полей и какие значения допустимы. Вектор хранит смысл, а метаданные дают призмы, через которые этот смысл можно быстро и точно сфокусировать.

## **Важность RAG для архитектора**

1. **RAG — это современный паттерн интеграции ИИ.** Благодаря ему вы понимаете, как сегодня встраивают ИИ в прод.
2. **Практика проектирования data-heavy сервисов.** Вопросы шардирования, кеширования, SLA, cold vs hot storage и векторных БД — всё из учебника по архитектуре, только на реальных примерах.
3. **Сшивка ML и классического бэкенда.** Нужно соединить пайплайн эмбеддингов, индексы, API и оркестрацию — отличный кейс о том, как «склеивать» разные технологические слои.
4. **RAG даёт микросервисное мышление.** Генерация, поиск, ранжирование и постпроцессинг легко раскладываются на отдельные сервисы; это помогает отточить навыки границ, контрактов и масштабирования.

## 8 шагов RAG

Пройдём весь процесс построения RAG от пользовательского до итогового ответа модели.

![[General/10 💼Карьера, работа/🎓Обучение профессиональное/Архитектор ПО/Sprint 07.2 Создание AI ассистента/attachments/99c8364025772a093235438fb351ec22_MD5.png]]

**Шаг 1. Препроцессинг запроса** Изначальную фразу пользователя нужно привести в надлежащий вид: убрать лишние пробелы, нормализовать кавычки и определить язык. Цель — не исказить смысл и при этом понять, какие фильтры можно включить.

**Шаг 2. Embedding и фильтрация** Запрос превращается в вектор той же моделью, что и документы (Sentence-BERT, e5, … ). Одновременно применяются жёсткие фильтры по метаданным: языку, дате, категории. Чем раньше сузится пространство поиска, тем меньше будет счёт за токены.

**Шаг 3. Recall: быстрый ANN-поиск** Дальше вектор попадает в индекс (Qdrant, FAISS, Weaviate — принцип один). Для этого берётся широкий черновик из примерно 50–100 чанков и с помощью низкого порога похожести отсекаются явно нерелевантные только метаданными. Этот слой работает на полноту.

**Шаг 4. Rerank: точная сортировка** Кандидаты проходят через кросс-энкодер, или гибридную формулу (векторная близость + BM25 + бизнес-скор). По итогу останется топ-10 наиболее релевантных фрагментов.

**Шаг 5. Trim: в контекстное окно** Теперь нужно сложить длины чанков и вопроса и свериться с лимитом модели (GPT-3.5 ≈ 16 k, GPT-4o ≈ 128 k). Если не помещаемся — режем хвост или удаляем повторяющиеся или служебные абзацы. В крайних случаях можно применить локальную компрессию, когда берутся только ключевые предложения.

> **Обратите внимание, что шаги 4 и 5 опциональны.**

**Шаг 6. Prompt compose** На этом шаге нужно сформировать системное сообщение («используй только этот контекст…») и вставить сначала пронумерованные чанки, а затем — запрос пользователя. Важные фрагменты должны стоять выше, потому что LLM читает сверху вниз.

**Шаг 7. LLM-ответ** Модель, не имея всей базы «в голове», опирается на свежий контекст и выдаёт точный и проверяемый текст. Заранее просим ссылаться на источники квадратными скобками — в постобработке заменим номера на URL из метаданных.

**Шаг 8. Post-processing** В финале нужно почистить двойные пробелы, единообразно отформатировать ссылки, при необходимости добавить markdown-заголовки или прогнать быстрый regression-check («Проверь, не придуманы ли факты. Есть ли все ссылки?»). В итоге на выходе получится связный ответ плюс набор использованных чанков для UI-подсветки и аудита.

## Архитектура данных

Зная цену токена и пределы окна, архитектор балансирует полноту и правдоподобие: меньше чанков — меньше «галлюцинаций», больше чанков — выше шанс найти редкий факт. Главное преимущество схемы — её расширяемость. Чтобы «доучить» систему, достаточно добавить или обновить документы в векторной базе без переобучения самой LLM.

**Кастомизация по точкам цепочки**

|Стадия|Что можно тюнить|
|---|---|
|Embedding|Своя модель под доменную лексику или редкий язык|
|Фильтр|Сложные правила: дата > подписка_активна|
|Recall size|Баланс скорость / риск пропустить ответ|
|Reranker|Лёгкий bi-encoder ↔ тяжёлый cross-encoder (про это будет дальше)|
|Trim-логика|«Короткие, но много» vs «мало, но длинные»|
|Prompt-шаблон|Тон, структура, требования к цитатам|
|Post-processing|Ссылки, обезличивание, автоперевод|

Таким образом, каждая стадия может подчиняться бизнес-логике, чтобы в итоге получилось уложиться в бюджет. В этом и заключается инженерная магия RAG.

Дальше мы рассмотрим два архитектурных инструмента, которые помогают сделать детальный тюнинг, хотя полноценный RAG можно создать и без них.

### Bi-encoder vs Cross-encoder

|Характеристика|**Bi-encoder**|**Cross-encoder**|
|---|---|---|
|**Как работает**|Каждую сторону (документ и запрос) кодирует отдельно. Векторы кладутся в индекс, сравнение — простое расстояние|Склеивает «запрос + документ» в один текст и прогоняет через модель. Похожесть — по последнему [CLS]-логиту|
|**Скорость**|_Миллионы_ сравнений в миллисекунды за счёт ANN-поиска; инференс только над запросом|Инференс на **каждую пару** ⇒ десятки–сотни мс на 100 пар (≈ 1 K FPS на A100 — только с батчингом)|
|**Память / индекс**|Векторы занимают 4–8 байт на компоненту; легко держать >100 M документов|Индекс не нужен, но на ранжирование приходится держать текст кандидатов в RAM или БД|
|**Точность (Top-k recall / nDCG)**|Хуже ранжирует «тонкие» различия (сложные связки, отрицания, длинные контексты)|Выше качество за счёт внимания между токенами запроса и документа|
|**Обучение**|Контрастивный loss, пары _позитив–негатив_; быстрее и дешевле|Point-wise или pair-wise классификация, часто требует больше примеров и времени|
|**Лучшие задачи**|Первая фаза поиска, огромный корпус, real-time автодополнение|Финальный rerank Top-N, FAQ-ответы, чувствительные к деталям юристика|
|**Минусы**|Теряет нюансы, чувствителен к длине вектора, сложнее учесть порядок токенов двух текстов|Дорого по GPU, плохо масштабируется для _миллионов_ документов|

А теперь, когда вы понимаете характеристики обоих инструментов, соединим их в два шага.

**Шаг 1. Поиск (Bi-encoder)**

- Запрос → embedding.
- ANN-индекс (FAISS/Qdrant/Weaviate) возвращает, например, Top-100 кандидатов за меньше, чем 50 мс.

**Шаг 2. Rerank (Cross-encoder)**

- Склеиваем каждый кандидат с запросом: "[CLS] {query} [SEP] {doc_chunk}".
- Прогоняем батчем через cross-encoder, получаем более надёжные оценки релевантности.
- Сортируем и берём финальные Top-k (обычно 5-20).

Такое «coarse-to-fine» даст баланс:

- **Скорость:** 100 паров × 1 мс ≈ 100 мс GPU-времени — приемлемо для запроса пользователя.
- **Качество:** cross-encoder убирает «мусор» и подтаскивает документы, где нюансы важны (отрицания, числа, формулы).
    

**Тонкая настройка**

- **Размер кандидатов.** 50–200 — золотая середина: больше — растёт латентность, меньше — падает recall.
- **Batch size** для cross-encoder. Чаще всего 16–32 примера на GPU даёт лучший throughput.
- **Смарт-sampling.** Если bi-encoder даёт оценку схожести, можно сразу отсеять кандидатов ниже порога, чтобы не гонять их через cross-encoder.
- **Кеширование** результатов cross-encoder для частых запросов или горячих документов уменьшает счёт за GPU.

Комбинация этих двух инструментов превращает «широкий и быстрый» bi-encoder-поиск в «узкий и точный» результат, не теряя отзывчивости. В итоге такое сочетание становится классическим последним штрихом, чтобы повысить качество выдачи перед тем, как передать контекст в LLM или вывести пользователю.

## Prompting-техники

Большая модель как собеседник-полиглот: она умеет почти всё, но тонко реагирует на то, **как** с ней разговаривают. Если формулировка запроса размыта, то GPT начинает гадать. А если пример неудачный, то копирует ошибки. Поэтому дальше вас ждут два приёма, как этого избежать. Речь пойдёт про **zero-shot** (без примеров) и **few-shot** (с примерами), а также про **Chain-of-Thought (CoT).**

### Zero-shot

Иногда можно обойтись без примеров, а достаточно чёткой инструкции. Главное — быть конкретным и задать границы.

```
Ты — корпоративный бот-ассистент. Отвечай коротко, по-русски, добавляй ссылку на документацию, если она есть в контексте.  

Контекст:
1. У нас в компании нет настроенных репликаций, у нас маленькая бд и это нам не нужно (23.05.2020)
2. В рамках задачи 5238 мы сделали логическую репликацию бд Postgres control panel (21.02.2022)
3. Логическая репликация не подошла, пришлось заменить на физическую (23.02.2022)
4. В рамках задачи 54364 мы сделали Read-Only реплику для всех наших 8 корпоративных баз данных (14.10.2024)

Вопрос:
Как настроена репликация у нас в компании? 
```

**Ответ RAG**

Сейчас работает физическая read-only репликация для всех 8 корпоративных БД (14.10.2024, задача 54364). Документация: смотрите описание задачи 54364 в трекере.

**Почему работает**

- «Ты — техподдержка» задаёт роль.
- Просим «коротко» и «по-русски» — получаем лаконичный ответ без английских вставок.
- «Добавляй ссылку, если она есть» заставляет модель поискать URL в контексте и не придумывать новые.

**Где может сломаться** Если роли нет или указана смазанно («Ты — помощник»), модель начинает болтать «в целом о репликации», не отвечая конкретно.

### Few-shot

Когда вопрос пользователя сложный или у текста особенный стиль, модели нужно показать несколько эталонных примеров.

```
Ты — юридический консультант. Давай только факты, без советов.  

Формат ответа:
1. Краткий вывод (1 предложение)
2. Цитата закона
3. Ссылка

Пример:
Q: Нужно ли индивидуальному предпринимателю вести кассу?
A: 
1. Да, при работе с наличными обязательна онлайн-КАССА.  
2. «Федеральный закон №54-ФЗ, ст. 1.2»  
3. https://…

---

Контекст:
<<<
…чанки…
>>>

Вопрос:
Обязателен ли договор NDA для сотрудников по ТК РФ? 
```

**Ответ RAG**

```
1. Нет, ТК РФ не обязывает заключать с сотрудником отдельный NDA; условие о неразглашении включается только по соглашению сторон.
2. «ТК РФ, ст. 57, ч. 4: в трудовом договоре могут предусматриваться дополнительные условия, в частности — о неразглашении охраняемой законом тайны (государственной, служебной, коммерческой и иной)».
3. [https://www.example.com/nda](https://www.example.com/nda) 
```

**Почему лучше**

- Шаблон и чёткий пример превращают абстрактный «ответь» в понятное «следуй формату».
- Модель повторяет структуру, держит тон и вставляет ссылки так же, как в примере.
    

**Где может сломаться**

- Примеры должны быть без ошибок и лаконичными. Чрезмерно длинный пример «съест» контекстное окно.
- Не смешивайте стили: если эталон официальный, не добавляйте шуток в другом примере.
    

### **Chain-of-Thought (CoT)**

**Chain-of-Thought (CoT)** — это приём, когда LLM просят сначала расписать внутреннее рассуждение «по шагам», а уже потом выдать конечный ответ. Такой подход часто повышает точность модели на логических и многошаговых задачах, потому что принуждает её явно разбить проблему на подпункты.

**Ответ RAG**

Представьте задачу: «У Вани три коробки, в каждой из которых по четыре пачки карандашей. В свою очередь, каждая пачка содержит 12 карандашей. Ваня подарил другу 15 карандашей. Сколько осталось?». Наивная модель может сразу угадать число и промахнуться. А с помощью CoT мы заставим её сначала посчитать общее количество карандашей, затем вычесть подаренные и проверить на отрицательные значения.

Развёрнутое CoT-рассуждение выглядит так:

- Три коробки × четыре пачки = 12 пачек.
- 12 пачек × 12 карандашей = 144 карандаша всего.
- Если Ваня подарил 15 карандашей, то после у него останется 144 − 15 = 129. А значит, правильный ответ — 129.

Даже если все шаги простые, то подобное явное проговаривание снизит риск того, что модель забудет один множитель или перепутает порядок.

Ещё можно добавить самопроверку («Санити-чек»): 15 — значительно меньше 144, так что результат должен быть чуть меньше исходного. А значит, 129 выглядит разумно. Такие лёгкие проверки улучшают устойчивость в задачах с несколькими арифметическими стадиями.

В более сложных доменах (логические головоломки, планирование эксперимента, SQL-трансформация данных) CoT разбивает задачу на подцели: извлечь факты, ввести обозначения, преобразовать, сверить ограничения, вычислить итог. Даже простая маркировка шагов «Шаг 1… Шаг 2…» уже даст выгоду.

**Почему лучше**

- CoT помогает модели «не прыгать к ответу», а удерживать промежуточные переменные в текстовой памяти. Это особенно важно, когда задача требует нескольких преобразований: извлечь числа, сопоставить категории, применить формулу и проверить граничные условия. Без такого шага модель может «потерять» одно из чисел или применить не ту операцию.
- В сочетании с RAG CoT снижает риск поверхностного копирования фрагмента контекста. Модель учится собирать релевантные факты из разных retrieved-источников, приводить их к общей шкале или формату и выводить результат. Так CoT превращает «чтение с цитированием» в «обоснованное заключение по материалам».
- CoT также повышает проверяемость. Когда есть пошаговая трассировка, человек или последующая проверочная модель (self-consistency, debate, verifier) может обнаружить, на каком шаге произошла ошибка. Это работает как интерпретируемость «в текстовом приближении»: пусть шаги не гарантируют истинный латентный расчёт модели, но они дают крючки для аудита.
- Наконец, CoT облегчает автоматические метаприёмы: majority voting по нескольким сэмплам рассуждений, ранжирование по критериям качества и рефлексия («Посмотри на свои шаги — нет ли несоответствия?»). Эти надстройки статистически улучшают точность на сложных бенчмарках, особенно когда один прогон может ошибиться, но вся цепочка шагов повышает шансы, что в итоге всё будет правильно.

**Где может сломаться**

- **Длинные цепочки → галлюцинации.** Модель может придумать шаги, которые выглядят логичными, но не основаны на retrieved данных. Это особенно опасно при слабом контроле над источниками.
- **Высокая цена токенов.** CoT увеличивает контекст, особенно в «открытом виде» (если выводим рассуждение в ответ). Для RAG + CoT это ещё дороже, потому что добавляем retrieved документы.
- **Неуместное применение.** CoT полезен в задачах reasoning, но для простых фактов (например, «Когда основан AWS?») этот приём может оказаться избыточным и даже запутать модель.
- **Утечка промежуточного reasoning.** Если разработчик случайно вернёт «черновик» пользователю, то могут возникнуть ошибки UX или модель раскроет внутреннюю логику, что иногда нежелательно.

### Что это даёт в UI чат-ботах

|Цель|Как выглядит в интерфейсе|На что обратить внимание|
|---|---|---|
|**Прозрачность & доверие**|Кнопка «Показать ход мыслей» или разворачивающийся блок с CoT|Пользователь видит, откуда взялся вывод, проще ловить ошибки|
|**Отладка и аналитика**|CoT выводится только в режиме “debug” или логируется в бэк-офис|Помогает улучшать промпт и ловить галлюцинации, не засоряя UI|
|**Лаконичность**|CoT генерится, но сразу сворачивается в краткое резюме («Пояснение»)|Экономит токены в выдаче, но сохраняет точность|

> ⚠️ Если показываете CoT прямо в чате, следите, чтобы в нём не просочились личные данные пользователя или внутренние системные инструкции.

**Как внедрить CoT в LangChain**

Добавьте инструкцию. Например: «_Думай шаг за шагом_» или _"Show your chain of thought"_. Можно хранить шаблон отдельно и переиспользовать.

CoT — простой, но мощный приём. В LangChain он реализуется парой строк, в UI его можно либо показать пользователю, либо скрыть для служебных нужд, сохраняя при этом прирост качества ответа.

### Плохие промпты

```
Контекст:
…  

Вопрос: репликация qdrant? 
```

**Что не так:** слишком коротко. Модель не знает, о чём именно её спросили, — про шардинг или синхронизацию.

```
Привет, GPT! Дай подробное объяснение, если можешь, но можешь и кратко… 
```

**Что не так:** без рамок. Запрос противоречивый, поэтому модель выбирает сама и плывёт.

### Структура промпта для RAG, проверенная на практике

```
[System]  Инструкция и роль
[Examples] (опционально, 1-2 штуки)
[Context]  <<< чанки с источниками >>>
[User]    Вопрос 
```

_System_ всегда должен идти первым. Это железное правило. _Examples_ сразу за ним, потому что к ним применяется тот же тон. _Context_ отделяем заметными маркерами (<<< >>>) — так модель учится, что брать факты только отсюда. _User_ вопрос в конце, чтобы остаться у модели «в рабочей памяти».

Ниже вас ждёт шаблон промпта (инструкция + формат) для RAG‑системы на русском. Он рассчитан на то, чтобы модель сначала внимательно изучила найденные документы, а затем выдала проверяемый, краткий и цитируемый ответ.

```
### Роль
Ты — крупная русскоязычная LLM‑модель‑ассистент.  
Твоя задача — аккуратно ответить на вопрос пользователя, используя ТОЛЬКО информацию из предоставленного списка документов.  
Если в документах нет нужной информации, честно скажи «Не нашёл подтверждений».  
Избегай домыслов и галлюцинаций.

### Шаги работы
1. Внимательно прочитай все документы из блока <Документы>.  
2. Определи, какие из них действительно релевантны вопросу.  
3. Сконспектируй ключевые факты (можешь делать пометки для себя, но не показывай их пользователю).  
4. Сформулируй итоговый ответ на русском, опираясь только на подтверждённые факты.  
5. В конце ответа проставь цитаты вида [1], [2] — это номера документов из блока <Документы>, которые подтвердили конкретное утверждение.

### Формат выдачи
Ответ должен состоять из двух частей:
**A. Краткий ответ** (1‑3 предложения).  
**B. Развёрнутое объяснение** (по пунктам), где каждый тезис снабжён ссылкой‑номером на источник в квадратных скобках.

### <Документы>
[1] {{doc1_title}} — {{doc1_excerpt}}  
[2] {{doc2_title}} — {{doc2_excerpt}}  
[3] {{doc3_title}} — {{doc3_excerpt}}  
… (может быть до N документов)

### <Вопрос пользователя>
{{user_question}}

### <Твой ответ>
(Соблюдай формат A. и B., как описано выше) 
```

**Как использовать**

1. Подставьте в блок <Документы> извлечённые фрагменты (title + snippet) поисковой выдачи или системы векторного поиска.
2. Поместите исходный вопрос пользователя в <Вопрос пользователя>.
3. Отправьте сформированный промпт модели.
    

Такой шаблон задаёт чёткие правила: модель обязана ссылаться на конкретные документы, не придумывать факты и выдавать структурированный, легко проверяемый ответ.

### Инструкции, ограничения и ссылки

Эти пункты можно добавлять в любую часть промпта. Поэкспериментируйте и найдите для себя наилучший подход.

- **Тон:** «пиши дружелюбно», «официальным стилем», «без эмодзи».
- **Формат:** «список маркдаун-пунктов», «JSON-ответ без комментариев».
- **Ссылки:** «добавь [1] после факта, потом список источников».
- **Запреты:** «не упоминай информацию вне контекста», «не генерируй код, если не попросили».
    
    Чем строже и короче правило, тем меньше шансов на галлюцинации.
    

### Тримминг и адаптация стиля

Когда найденных чанков настолько много, что модель начинает теряться в фактах, стоит сначала урезать повторы и подписи авторов, потом — длинные цитаты, чтобы в итоге осталось ядро фактов. Если стиль важен (например, корпоративный гайд), добавляем в System-часть короткий reference-snippet, которому модель будет подражать.

**Reference-snippet** — это небольшой отрывок текста, который написан **в нужном стиле** (например, деловой, научный, маркетинговый) и используется как **пример для подражания** внутри System-промпта LLM.

Когда вы добавите такой snippet в System-промпт (_«Следуй стилю следующего текста…»_), модель будет подражать его тону, лексике, структуре и ритму, даже если основная информация будет поступать из более нейтральных или разностилевых чанков.

**System-подсказка:**

```
Ты корпоративный ассистент. Отвечай строго в стиле, похожем на этот фрагмент:

"Мы придерживаемся принципов прозрачности, уважения к партнёрам и точности в коммуникации. Каждый ответ должен быть кратким, вежливым и деловым."

Если информация повторяется или незначительна — сокращай. Главный приоритет — ясность и ценность для читателя. 
```

Такой snippet позволяет модели стилистически «настроиться» перед генерацией. Это особенно важно, если основной контент — просто сухие факты из базы.

## Как выбирать чанки

Когда мы говорим о RAG-системе, поиск — это только половина дела. Даже если вы нашли 20–30 потенциально релевантных фрагментов, не все из них стоит передавать в генеративную модель: контекст ограничен, а лишние или неточные данные могут сбить, что приведёт к неправильному ответу. Поэтому ключевая задача — выбрать лучшие чанки, то есть те, что не только похожи на запрос, но и содержат точную и проверенную информацию, которая к тому же оформлена в нужной для генерации форме.

Рассмотрим четыре простые стратегии, которые как раз и помогут выбрать нужные фрагменты, а также идею, как их сочетать.

|Критерий отбора|Что измеряем|Главная сила|Подводные камни|Когда особенно полезен|
|---|---|---|---|---|
|**Косинусное сходство**|Расстояние между вектором запроса и вектором чанка|Мгновенно работает прямо в БД, ничего не стоит|Слепо гонится за «похожестью», игнорируя длину и редкие токены|Первый фильтр: оставить Top-k перед более тяжёлым ранжированием|
|**Оценка кросс-ранжировщика**|Уверенность модели, которая видит запрос и чанк одновременно|Ловит тонкие нюансы, отрицания, числа|Медленнее: 5–10 мс на пару даже на GPU|Финальный отсев, когда нужны 5–10 «самых-самых»|
|**Длина чанка**|Количество токенов|Позволяет набрать больше фактов в лимит, не раздувая prompt|Слишком короткие фрагменты теряют контекст|Сбор справок, списков, FAQ, где важна широта охвата|
|**Матч по ключевым словам или метаданным**|Наличие конкретных терминов, даты, языка, категории|Гарантирует, что редкие коды, артикулы, даты не выпадут|Легко переусердствовать и отбросить полезный «общий» текст|Техподдержка, юридические ответы, каталоги товаров|

**Как это выглядит в коде**

```
# Уже получили 20 кандидатов из ANN-поиска
candidates = ann_search(query_vec, top=20)

# 1. Cosine оставляем первые 15
candidates = sorted(candidates, key=lambda x: x.cosine_sim, reverse=True)[:15]

# 2. Reranker переоценивает и даёт новый score
scores = cross_encoder.predict([(q, c.text) for c in candidates])
for c, s in zip(candidates, scores):
    c.cross_score = s

# 3. Подсвечиваем редкие ключи — +0.1 за каждое совпадение
for c in candidates:
    if any(k in c.text.lower() for k in ["ndfl", "form 2-nfdl"]):
        c.cross_score += 0.1

# 4. Итог: топ-5 по cross_score, причём если длина > 350 токенов — урезаем
final = sorted(candidates, key=lambda x: x.cross_score, reverse=True)[:5]
for c in final:
    if c.tokens > 350:
        c.text = trim_to_tokens(c.text, 350) 
```

# Итоги

RAG совмещает поиск по векторному индексу с генеративной моделью, но, чтобы LLM не приходилось «помнить» всё на свете, для неё создаётся векторная база — внешний источник «знания», где каждый документ хранится как эмбеддинг.

Когда на пользовательский запрос находятся наиболее релевантные векторы, в игру вступают специализированные хранилища: FAISS, Pinecone, Qdrant и ChromaDB.

Если перед вами стоит задача построить полный RAG-pipeline, то начать стоит с FAISS. Эта библиотека предназначается, чтобы находить ближайшие соседние векторы в больших наборах данных.

FAISS стоит применять, если требуется скорость и автономность, полный контроль и лёгкий вход.

Однако у FAISS есть ограничения, поэтому могут потребоваться «векторные системы управления базами данных». Самые популярные — Pinecone, Qdrant и Chroma. Pinecone подойдёт, когда нужна «база как сервис». Qdrant идеален для локальной разработки и продакшена. А Chroma — вариант для Пайтона.

Если в векторный поиск добавить фильтры, то он начнёт работать куда точнее.

Весь процесс построения RAG от пользовательского до итогового ответа модели состоит из 8 шагов, из которых два опциональны.

Зная цену токена и пределы окна, архитектор балансирует полноту и правдоподобие: меньше чанков — меньше «галлюцинаций», больше чанков — выше шанс найти редкий факт. Главное преимущество схемы — её расширяемость.

Если формулировка запроса размыта, то GPT начинает гадать. А если пример неудачный, то копирует ошибки. Справиться с этим помогут две техники промптинга — zero-shot (без примеров) и few-shot (с парой образцов).
